# Surviving mutants, explained

`npm run test:mutation:core [-- --set=<set>|all]` (`tools/mutate.ts`, 4.1.0 "Clarity"; the sets in
`tools/mutation-sets.ts`) mutates a set's sources one operator at a time and runs the tests that judge that set
against each mutant. Each set is named for exactly the files it mutates (4.1.19, plan §8.1):

| Set | Mutates | Gate |
|---|---|---|
| `core` | `src/engine/core/{cond,save,session-runtime,migrate}.ts` | gated |
| `reality` | the engine's receive, the protocol, the client, the HTTP port; the Bridge, its journal store, lock and policy | gated |
| `runs` | the speedrun queue: `bridge/src/{runs,runs-store,runs-limiter}.ts` | gated |
| `remix` | a world's seed, compilation, application, categories; the Daily and Mystery tokens | gated |
| `speedrun` | a run's envelope, the recorder, the verifier | gated |
| `connectors-pure` (`connectors` until 4.2) | the connectors' pure parts: SDK, MIME reader, line editor, virtual disk, badge crypto and fetch | gated |
| `reality-store` | the Bridge's stores in memory, SQL and SQLite, migrations, streams, signing (not the Postgres adapter) | gated |
| `connectors-edge` | configuration and start, the email connector (webhook, IMAP, parse), badge verification, terminal guard and shell, SSH, Telnet | gated (4.1.20) |
| `reality-store-postgres` | `bridge/src/store-postgres.ts`, judged on a Postgres (its own database per test file, the files one after the other) | gated (4.1.20) |
| `studio-ops` | the Studio Server's journal, its durable writes and the spans of a game's files | gated (4.2.1) |
| `studio-auth` | the Studio Server's gate, OpenID provider, auth routes and store, spans' leases, the game's origin | gated (4.2.1) |
| `studio-workshop` | the Studio Server's personal undo, health by revision, previews, builds, prepared assets, backup, journal shipped and collection | gated (4.2.3) |

A gated set fails its job on any survivor not named below; a measured set reports, toward being read and gated. The
survivors named here are equivalent mutants: no input the engine or the Bridge can receive tells them from the
original. Each is in `docs/dev/mutants.json` (file, operator, from, to, context, why), which is what the gate reads; a
name whose mutant no longer survives is reported as stale. This page explains them; the JSON file is the list.

Since 4.1.20 (plan §7.4) an entry is an exemption with its terms: a `category` (`equivalent`, `unreachable`,
`instrumentation`, `out-of-contract`), its `why`, a `proof` (`argument` for an equivalent mutant, where the why is the
proof; a test file otherwise), an `owner` and a `revisit` version from which it is refused until it is read again. A
An entry due stops every set, whatever its file: it is read again before any release of that version. A
long set runs in shards (`--shard=i/n`, `SHARDS` in `tools/mutation-sets.ts`), merged into its report (`--merge`) by
a step that refuses a shard missing, doubled, cancelled or of other inputs.
