# Jack cherche un taf – notes for an AI assistant

A point-and-click game by Anna (12) and Horacio, made with quest'n'click (formerly web-scumm). This repository holds
**only the game**: the engine is the npm package `@quest-n-click/engine` (in `node_modules`, never edited there by
hand except through `patches/`, below). The engine's documentation is its wiki,
https://github.com/Quest-n-Click/quest-n-click/wiki (also searchable through the MCP tools `search_docs` / `read_doc`).

## Where things are
- `game/` – the game: `game.ts` (verbs, map, start, ui texts), `cast.ts`, `items.ts`, `rules.ts`, `rooms/*.ts` (one per
  room), `layout/*.json` (geometry, written by the editor), `art/` (cut sprites; `art/sheets/` the source sheets),
  `audio/` (with `palette.json`, the game's sound bank), `locales/` (en, es; French is the source), `storyboard.json` (the script), `site.json`, `index.ts`,
  `tests/game.test.ts`, `ART_BRIEF.md` and `prompts*.md` (the image model's brief), `art-tools/` (small cleanup scripts).
- `game/private/` – raw sheets, photos: gitignored, never committed.
- `patches/` – changes to the engine package not yet in a release (see below).
- `public/` – icons, font, og.png; `public/assets` is generated by `npm run assets` and not committed.

## Commands
```
npm run dev              # the game; ?dev&at=<checkpoint> jumps to a state, ?edit=<room> the placement editor
npm run dev -- --host    # the same on the local network (a phone, in landscape)
npm run studio           # the Studio
npm run validate         # references, missing look lines, minigame params
npm run solve            # proves the game can be finished from New Game
npm test                 # the game's walkthrough test (vitest)
npm run verify           # validate, solve, i18n status, lint, playtests
npm run build            # assets, verify, dist/ (BASE_PATH=/web-scumm-jack-cherche-un-taf/ for GitHub Pages)
npm run i18n -- status   # translations
npm run cut-sheet -- game/art/sheets/<sheet>.png <sheet-id> [--grid 6x4] [--cells r1c2] --scale 2 --colors 64
npm run audio -- all game/audio/projects/<slug>/spec.json   # the Mega Drive pipeline (sfx: audio -- sfx game/audio/sfx.json)
```
`game/prompts.md` and `prompts-episode2.md` were adjusted by hand after generation (background colour, 2x pixel
grid, see `ART_BRIEF.md`): never regenerate them over the originals. The engine's `quest-n-click prompts` rewrites
`game/prompts.md` and, in 4.5.3, writes wrong paths for a project (`../../../game/art`).

Always absolute paths in shell commands (`npm --prefix /abs/path run …`), never `cd X && cmd relative/path`.

## Rules that keep the game healthy
1. Content is data. No functions in `game/`. Logic is a condition (`if`) or a command (`do`).
2. Logic in `rooms/*.ts`, geometry in `layout/*.json`: never type coordinates by hand, use `?edit=<room>`.
3. Every visible thing has a `look`. Every action gets an answer (fallbacks in `rules.ts`).
4. The storyboard is the source of truth for text: change `storyboard.json` first, then the room. Translations follow
   with `npm run i18n -- extract --lang en` (then `es`).
5. After any content change: `npm run validate && npm run solve && npm test`. After a visual change: a screenshot.
6. Old art versions (`_v1`…) can be deleted once the new one is validated and committed. Never commit `private/`.
7. Jack's lines are short, funny and kind. Repeated looks: normal, normal, normal, absurd.
8. Writing: English uses the spaced en-dash ( – ), never the em-dash; French and Spanish no mid-sentence dash at all.

## Patching the engine (`patches/`, patch-package)
When the game needs an engine change before a release has it:
1. Make the change in the engine repository first, as a pull request with its test and wiki page
   (Quest-n-Click/quest-n-click; Horacio co-maintains it).
2. Apply the same change to `node_modules/@quest-n-click/engine/…`, then `npm run patch -- @quest-n-click/engine`:
   it rewrites `patches/@quest-n-click+engine+<version>.patch` (one file per package, all its changes).
3. Commit the patch with the game change that needs it, and say in the commit which PR it comes from.
4. The patch is applied by `postinstall` (on CI), and again by `dev`, `studio`, `validate`, `solve`, `verify`, `test`,
   `build` and `release` (`patch-package` first: Horacio's npm has `ignore-scripts=true`, so `postinstall` never runs on
   his machine). Applying it twice is harmless.
5. When a release contains the change: bump `@quest-n-click/engine` in `package.json`, `npm install`, delete the
   patch's hunks that the release now has (or the whole file), check the fuse box or whatever the patch fixed.
   `patch-package --error-on-fail` stops every command if a patch no longer applies: that is the signal.
